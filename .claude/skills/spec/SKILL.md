# /spec — 機能の仕様を書く

機能づくりの最初の工程。`docs/features/<機能名>.md` に仕様を書き、人の確認を得て確定させる。
流れの全体は `docs/decisions/0006-issue-workflow.md`。

対象の機能: $ARGUMENTS

## この skill でやらないこと

- issue を作らない（次の工程 `/issues` で行う）
- コードを書かない、ファイル名を決める以外の設計（テーブル定義など）に踏み込まない
- 仕様の内容を人に代わって決めない。決まっていないことは「未決定のこと」に残す

## 手順

### 1. 準備

1. 対象の機能が指定されていなければ、どの機能の仕様を書くか質問して止まる
2. 次のドキュメントを読む
   - `docs/product.md`（目的、大事にすること、ロードマップ）
   - `docs/architecture.md`（構成と守るルール）
   - `docs/decisions/` のうち関係するもの
   - `docs/features/_template.md`
3. ファイル名を決める。`docs/features/<短い英語名>.md`（例: `weight.md`）。英語名は人に確認する
4. そのファイルがすでにあれば、内容を要約して示し、「修正する」か「やめる」かを質問して止まる

### 2. 質問する

下書きを書く前に、仕様の中心になることを質問する。

- 一度に聞くのは **3つまで**。選択肢があるものは選択肢とおすすめを示す
- 主に聞くこと
  - 目的（この機能で何ができるようになりたいか）
  - 記録する項目（項目名、必須かどうか、単位）
  - 画面と操作（入力、一覧、グラフ・集計、編集・削除）
- 回答を待つ。推測で埋めない

### 3. 下書きを書く

- `docs/features/_template.md` をもとに書く。状態は `下書き` にする
- 回答で決まったことだけを書く。決まっていないことは「未決定のこと」に書く
- 次の方針を反映する
  - 「入力の手軽さ」を最優先する（`docs/product.md` の「大事にすること」）
  - すべての記録はユーザーごとに分かれる（ユーザー ID を持つ）
  - 「受け入れ条件」は、人が画面で確認できる具体的な文にする（例: 「体重を入力して保存すると、一覧の先頭に表示される」）
  - 「今回はやらないこと」に、範囲外のものをはっきり書く

### 4. 確認してもらう

1. 下書きの要点と、「未決定のこと」に残した項目を示す
2. 修正があれば反映し、もう一度確認してもらう
3. 人が承認したら、状態を `確認済み` にする
4. 「未決定のこと」が残っている場合は、実装に影響するものかどうかを示し、承認前に決めるか人に判断してもらう

### 5. PR を作る

仕様は、issue を作る前に main に入れる（親 issue から main の仕様へリンクするため）。

1. 最新の `main` から `docs-<短い英語名>-spec` ブランチを作る（例: `docs-weight-spec`）
2. 仕様のファイルをコミットし、push して PR を作る。本文は `.github/pull_request_template.md` の形式で書く（issue がまだないため `Closes #` は書かない）
3. マージは人が行う

### 6. 終わり

- 作成・変更したファイルと PR の URL を示す
- 次の工程は `/issues <機能名>` であることを伝える。issue は、仕様の PR がマージされる前に作ってもよい（リンクはマージ後に開けるようになる）
