# /implement — サブ issue を実装して PR を作る

機能づくりの3番目の工程。1つのサブ issue を、1つのブランチ・1つの PR で実装する。
流れの全体は `docs/decisions/0006-issue-workflow.md`。

対象のサブ issue: #$ARGUMENTS

## この skill でやらないこと

- 計画の承認を得る前にコードを書かない
- サブ issue の範囲外の変更をしない。必要になったら、作業を止めて別のサブ issue を提案する
- 承認なしに新しいライブラリを入れない
- PR をマージしない（マージは人が行う）

## 手順

### 1. 準備

1. サブ issue の番号が指定されていなければ、質問して止まる
2. サブ issue を読む
   ```bash
   gh issue view <番号> --comments
   ```
   - 閉じている、またはサブ issue ではない（「親 issue」欄がない）→ 状況を伝えて止まる
3. 親 issue と、リンクされている `docs/features/<機能名>.md` を読む
4. 依存関係を確認する。先に終わっているべきサブ issue が開いたままなら、伝えて止まる
5. `docs/architecture.md` を読む。Next.js のコードを書く場合は、`web/AGENTS.md` に従い、`web/node_modules/next/dist/docs/` の関係するガイドを読む
6. 作業ツリーの状態を確認する
   ```bash
   git status
   ```
   未コミットの変更があれば、内容を示して止まる。勝手に退避・破棄しない

### 2. 計画を示して承認を得る

実装する前に、次の内容を示して **止まる**。

- やること（サブ issue の「やること」をどう実現するか）
- 変更・追加するファイル
- 新しく入れるライブラリ（あれば、理由と代わりの案）
- 完了条件をどう確認するか
- 判断に迷う点や、仕様・issue で決まっていない点（推測で埋めずに質問する）

修正があれば反映し、もう一度示す。承認されたら次へ進む。

### 3. ブランチを作る

最新の `main` からブランチを作る。ブランチ名は `<issue番号>-<短い英語名>`（例: `12-weight-table`）。

```bash
git switch main
git pull --ff-only
git switch -c <issue番号>-<短い英語名>
```

### 4. 実装する

- 承認された計画の範囲だけを実装する
- 計画から外れる必要が出たら、作業を止めて理由と新しい案を示し、承認を得る
- 構成を変えたら、同じブランチで docs も更新する（`docs/architecture.md` など）

### 5. チェックする

`web/` で次を実行し、すべて通るまで直す。

```bash
pnpm lint
pnpm exec tsc --noEmit
```

- 通らないまま次へ進まない。どうしても直せない場合は、止めて状況を伝える
- 画面を変えた場合は、開発サーバーで表示を確認できるなら確認する。確認できなかった場合は、そのことを報告に書く

### 6. コミットして PR を作る

1. コミットする。メッセージは日本語で、末尾に issue 番号を付ける（例: `体重テーブルを追加 (#12)`）
2. ブランチを push して PR を作る
   ```bash
   git push -u origin <ブランチ名>
   gh pr create --base main --title "<サブissueのタイトルから [タスク] を除いたもの>" --body-file <本文のファイル>
   ```
3. PR の本文は次の形式にする（本文の一時ファイルはリポジトリに残さない）

   ```markdown
   ## 概要
   <!-- 何をしたか、1〜3行 -->

   ## 変更内容
   - 

   ## 確認方法
   <!-- 人が確認する手順。サブ issue の完了条件と対応させる -->
   - [ ] 

   ## 確認できていないこと
   <!-- なければ「なし」 -->

   Closes #<サブissue番号>
   ```

### 7. 終わり

- PR の URL を示す
- 人に確認してほしい点（特に判断を含む変更）を短く示す
- 確認・マージは人が行うことを伝える。修正の指示があれば、同じブランチで直して push する
- 親 issue の残りのサブ issue を示す。すべて閉じたら、次の工程は `/finish <親issue番号>` であることを伝える
