# /finish — 機能を完了させる

機能づくりの最後の工程。機能が完成したことを確認し、ドキュメントの状態を「実装済み」にして、親 issue を閉じる。
流れの全体は `docs/decisions/0006-issue-workflow.md`。

対象の親 issue: #$ARGUMENTS

## この skill でやらないこと

- 受け入れ条件を、人の確認なしに「満たした」としない
- 開いているサブ issue を勝手に閉じない
- 次に作る機能を提案しない（順番は人が決める）
- PR をマージしない、親 issue を直接閉じない（PR のマージで閉じる）

## 手順

### 1. 準備

1. 親 issue の番号が指定されていなければ、質問して止まる
2. 親 issue を読む
   ```bash
   gh issue view <番号>
   ```
   - 閉じている、または親 issue ではない（タイトルが `[機能]` で始まらない）→ 状況を伝えて止まる
3. リンクされている `docs/features/<機能名>.md` を読む
4. 作業ツリーに未コミットの変更があれば、内容を示して止まる

### 2. サブ issue を確認する

```bash
gh api repos/{owner}/{repo}/issues/<親issue番号>/sub_issues --jq '.[] | "#\(.number) \(.state) \(.title)"'
```

- 開いているサブ issue があれば、一覧を示して止まる
- 閉じているのに PR がマージされていないサブ issue（PR なしで閉じたもの）があれば、一覧を示して、そのままでよいか質問する

### 3. 受け入れ条件を確認してもらう

親 issue と仕様の「受け入れ条件」を一覧で示し、人に確認してもらって **止まる**。

- それぞれの条件について、どのサブ issue（PR）で対応したかを添える
- 対応したサブ issue が見当たらない条件があれば、はっきり示す
- 満たしていない条件があると人が判断したら、追加のサブ issue を提案して止まる（`/issues` の手順で作成する）

### 4. ドキュメントを更新する PR を作る

人が受け入れ条件を確認したら、最新の `main` からブランチを作る。ブランチ名は `<親issue番号>-finish-<短い英語名>`（例: `10-finish-weight`）。

```bash
git switch main
git pull --ff-only
git switch -c <親issue番号>-finish-<短い英語名>
```

次を更新する。

- `docs/features/<機能名>.md`: 状態を `実装済み` にし、受け入れ条件のチェックを付ける
- `docs/product.md`: ロードマップの「機能づくり」で、この機能の状態を `完了` にする
- `docs/architecture.md`: 実装した内容が反映されていなければ更新する（✅ / 🔜 の印も直す）

コミットして PR を作る。コミットメッセージは `<機能名>を完了 (#<親issue番号>)`。

```bash
git push -u origin <ブランチ名>
gh pr create --base main --title "<機能名>を完了" --body-file <本文のファイル>
```

PR の本文（本文の一時ファイルはリポジトリに残さない）:

```markdown
## 概要
<機能名> の実装が完了したため、ドキュメントの状態を更新する。

## 完了したサブ issue
- #

## 変更内容
- 

Closes #<親issue番号>
```

### 5. 終わり

- PR の URL を示す。マージすると親 issue が閉じることを伝える
- マージは人が行う
- ロードマップの「機能づくり」で次にある機能を、書かれているとおりに伝える（順番の提案や変更はしない）。次の工程は `/spec <機能名>` であることを伝える
