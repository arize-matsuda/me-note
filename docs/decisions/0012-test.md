# 0012: テスト

- 日付: 2026-11-17
- 状態: 採用

## 背景

品質チェックは必要になったときに1つずつ入れる（[0005](0005-development-process.md)）。
機能づくりに入る前に、AI が書いた処理が正しく動くかを自動で確かめる仕組みを入れる。
テストの種類、道具、置き場所、実行のタイミング、最初に何をテストするかを決める必要がある。

## 決定

### テストの種類

- **今はユニットテスト（関数や部品を1つずつ確かめる）だけを入れる**
- E2E テスト（ブラウザを動かして、登録からログインまでの流れを確かめる）は、必要になったときに改めて決める

### 道具

- **Vitest** を使う（`web/vitest.config.mts`）
- `@/` で始まる import は、Vite の `resolve.tsconfigPaths` で解決する。Next.js 公式ガイドにある `vite-tsconfig-paths` は入れない
- 画面部品のテスト用のライブラリ（Testing Library、jsdom など）は、必要になったときに入れる

### 置き場所

- **テストする対象のファイルの隣に `<名前>.test.ts` として置く**（例: `web/src/proxy.ts` のテストは `web/src/proxy.test.ts`）

### 実行のタイミング

- **CI で実行する**。lint・型チェックと同じジョブに `pnpm test` を追加し、通らないと PR をマージできない
- CI のジョブ名「web (lint, typecheck)」は変えない。main の保護ルールで、マージに必要なチェックとしてこの名前が登録されているため
- **AI は「完了」と報告する前に `pnpm test` も通ることを確認する**

### テストを書く範囲

- **計算や入力チェックなどの処理を書いたら、テストも書く**
- 見た目だけの変更には書かなくてよい

### 最初のテスト

- `web/src/proxy.ts`（ログインしていない人を `/login` に移動させる判定）のテストを書く

## 理由

- E2E テストを CI で動かすには、テスト用の DB やアカウントの準備が必要で、大きな作業になる。まずは小さく始める
- Vitest は速く、TypeScript のまま少ない設定で動く。Next.js の公式ガイドもある
- テストを対象の隣に置くと、機能ごとのまとまり（`features/weight/` など）の中で完結する
- CI で実行すれば、AI が作った PR でも、テストが通らないものはマージされない
- `proxy.ts` はコードを変えずにテストでき、ログインまわりの守りにもなる

## 注意

- DB を読み込んで表示する画面（async のサーバーコンポーネント）は、Vitest では確かめられない。Next.js の公式ガイドでも、これらは E2E テストで確かめるよう案内されている
- Vitest 5 は `@types/node` 22 以上を求めているが、今は 20 のため、インストール時に警告が出る。動作には影響しない。更新が必要になったら、別の作業として行う
