# 0010: ログインの方法と画面

- 日付: 2026-11-17
- 状態: 採用

## 背景

ログインには Better Auth を使う（[0003](0003-hosting-database-auth.md)）。
ログインの方法、新規登録の扱い、ログインが必要な画面、画面の作り方を決める必要がある。

## 決定

### ログインの方法

- **メールアドレスとパスワード** でログインする
- パスワードは8文字以上
- Google アカウントやパスキーは、必要になったら後から追加する

### 新規登録

- **新規登録は制限しない**（誰でも登録できる）
- これにより、[0001](0001-users-and-devices.md) の「最初は新規登録を閉じておき、公開するときに開放する」は **置き換え** る

### ログインが必要な画面

- **ログイン画面（`/login`）と登録画面（`/signup`）以外は、すべてログインが必要**
- ログインしていない人が開くと `/login` に移動する。ログイン済みの人が `/login`・`/signup` を開くとトップに移動する
- この移動は `web/src/proxy.ts` で Cookie の有無だけを見て行う（大まかな判定）
- **データを扱うページ・Server Action では、必ず `getCurrentUser()`（`web/src/shared/auth/session.ts`）でセッションを確認する**。Cookie は偽物や期限切れのことがあるため

### 画面の作り方

- **画面部品には shadcn/ui を使う**。部品は `web/src/shared/components/ui/` に置く
- ログイン画面と登録画面は、shadcn/ui のテンプレート `login-01` と `signup-01` をもとに作る
- shadcn/ui が生成した部品（`src/shared/components/ui/`）は外部のコードとして扱い、Biome の lint の対象から外す（フォーマットは適用する）

## 理由

- メールアドレスとパスワードは、外部サービスの登録が不要で、1つずつ進めやすい。スマホのパスワード管理機能で自動入力もできる
- 新規登録を制限しなくても、すべての記録はユーザーごとに分かれ、ほかの人の記録は見えない（[architecture.md](../architecture.md) の「守るルール」）
- Next.js の公式ガイドでも、proxy での判定は大まかなものにとどめ、データの近くで必ず確認するよう推奨されている
- shadcn/ui はコードがプロジェクトに取り込まれるため、見た目を自由に変えられる

## 注意

- 公開（ステップ7）したあとは、URL を知っている人なら誰でもアカウントを作れる。知らない人のデータが DB（Neon の無料枠）に入る可能性がある。気になるようになったら、登録の制限を検討する
- パスワードの再発行は、メールを送る仕組みが必要なため、まだない
- `server-only`（サーバー専用のファイルを、ブラウザ用のコードから誤って読み込むのを防ぐ仕組み）は入れていない。入れる場合は独立したパッケージ `server-only` を追加する
- テーブル定義（`web/src/shared/auth/schema.ts`）は Better Auth の公式 CLI（`auth` パッケージ）で生成した。Better Auth の設定を変えたら、次のコマンドで作り直す
  ```bash
  DATABASE_URL=postgresql://placeholder@localhost/placeholder pnpm dlx auth@<better-authと同じバージョン> generate --config src/shared/auth/server.ts --output src/shared/auth/schema.ts
  ```
