# 0007: ブランチと PR の運用

- 日付: 2026-11-17
- 状態: 採用

## 背景

AI が作った変更を、人が PR で確認してから取り込む進め方にしている（[0006](0006-issue-workflow.md)）。
main の履歴を読みやすく保ち、誤った変更や事故から main を守る必要がある。

## 決定

### マージ

- **マージ方法は Squash merge だけにする**（Merge commit と Rebase merge は GitHub の設定で無効にする）
- **マージ後にブランチを自動で削除する**
- マージは人が行う

### main の保護（GitHub のルールセット「main を保護」）

- main への変更は **PR 経由のみ**。直接 push はできない
- **強制 push と削除を禁止** する
- 承認（Approve）は必須にしない
- 管理者も例外にしない

### PR テンプレート

- PR の書式は `.github/pull_request_template.md` にまとめる。skill（`/implement`、`/finish`）もこのテンプレートに従う

### ブランチ名

- issue がある作業: `<issue番号>-<短い英語名>`（[0006](0006-issue-workflow.md)）
- issue がない作業（土台づくりなど）: `<内容がわかる短い英語名>`（例: `setup-branch-and-pr`）

## 理由

- Squash merge にすると、main の履歴が「1コミット＝1つの PR（タスク）」になり読みやすい。AI が途中で何度コミットしても main はきれいなまま
- main を PR 経由に限ることで、AI が誤って main に push する事故を防ぐ
- 1人で開発しているため、承認を必須にすると自分の PR をマージできなくなる
- PR の書式を1か所にまとめることで、人が手で作る PR と skill が作る PR の書式がそろう

## 注意

- main を書き換えて強制 push すること（以前の `.DS_Store` の修正のような操作）はできない。修正はすべて PR で行う
- CI が通らないとマージできない設定は、CI を入れるとき（ロードマップのステップ4）に追加する
- PR #1 は設定を変える前にマージしたため、main には通常のマージコミットが1つ残っている
