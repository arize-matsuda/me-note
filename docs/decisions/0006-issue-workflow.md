# 0006: issue による機能とタスクの管理

- 日付: 2026-11-17
- 状態: 採用

## 背景

AI が実装し、人は承認と修正だけを行う進め方にしたい（[0005](0005-development-process.md)）。
そのためには、作業の単位をはっきりさせ、各工程で人が承認する場所を決めておく必要がある。

## 決定

- **1つの機能を親 issue、その中のタスクをサブ issue で管理する**
- **仕様は `docs/features/<機能名>.md` に書き、親 issue からリンクする**
- **issue は AI が案を作り、人が承認してから GitHub に作成する**
- **1つのサブ issue ＝ 1つのブランチ ＝ 1つの PR** にする
  - ブランチ名は `<issue番号>-<短い英語名>`（例: `12-weight-table`）
  - PR の説明に `Closes #<サブissue番号>` と書き、マージ時にサブ issue を自動で閉じる
- すべてのサブ issue が閉じたら、親 issue を閉じる
- 各工程は skill で進める（`/spec` → `/issues` → `/implement` → `/finish`）
- issue のテンプレートは `.github/ISSUE_TEMPLATE/` に置く（`feature.md`: 親 issue、`task.md`: サブ issue）
- 土台づくりのステップ（[product.md のロードマップ](../product.md#ロードマップ)）は issue で管理しない

## 流れ

| 工程 | skill | AI | 人 |
|---|---|---|---|
| 仕様 | `/spec` | 仕様の下書きを書く | 確認・修正 |
| issue 作成 | `/issues` | 親 issue とサブ issue の案を示し、承認後に作成する | 案を承認する |
| 実装 | `/implement` | 計画を示し、承認後に実装して PR を作る | 計画の承認、PR の確認とマージ |
| 完了 | `/finish` | 親 issue を閉じ、ドキュメントの状態を更新する | 確認 |

## 理由

- 仕様をリポジトリに置くことで、コードと一緒に履歴が残り、AI がいつでも読める。issue は進み具合の管理に専念させる
- 作業の単位（サブ issue）と承認の単位（PR）をそろえると、確認する範囲が小さく明確になる
- 工程を skill にすることで、毎回同じ手順で進み、各工程の最後に必ず人の承認をはさめる
